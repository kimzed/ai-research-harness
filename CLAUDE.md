# AI Research Harness -- Project Agent Instructions

This file states the conventions every project instantiated from this
template depends on -- and only those. All are load-bearing: read them
before writing any code or making any commit here. Anything negotiated with
the particular researcher using an instance is not here; see "Project
onboarding & the citation contract" below for where that lives.

## Starting a session on a fresh instance

Two states mean this instance is not ready yet. Both are visible from the
repo without asking the researcher anything, so notice them at the start of
a session rather than waiting to collide with them:

- **`SETUP.md` still carries `_not-yet-verified_` lines** -- the machine
  prerequisites have not been confirmed here. The `setup` skill probes them.
- **No `citation-contract.md` at the repo root** -- this instance has not
  been onboarded. The `onboarding` skill runs that conversation.

In both cases: **offer once, and never run either skill unasked.** Do not
re-offer after a decline in the same session -- the researcher knows where
their own project stands. **Never block what they actually asked for**: do
the work, and raise the gap only when it is what makes their request fail
(no TeX Live and they want a compile; no contract and they want a citation).
**When both are open, setup comes first** -- `onboarding`'s take-stock probes
Zotero, which needs the software installed before it can answer.

## Scoped-commit convention (CAP-9 / AD-9)

Every git commit Claude Code makes in this repo is scoped to exactly the
paths it wrote or changed in that turn.

- Never run `git add -A` or `git add .`.
- Before staging anything, run `git status` first.
- Stage only the specific paths written this turn (`git add <path> <path> ...`).
- For paths deleted or renamed this turn, use `git rm <path>` / `git add -u
  <path>` instead of a plain `git add` -- the same scoping rule applies.
- Any pre-existing uncommitted changes found in `git status` are left
  untouched and surfaced to the researcher -- never folded into a Claude
  Code commit.
- If a single path mixes pre-existing uncommitted changes with this turn's
  edits, stage only this turn's hunks with `git add -p <path>` (or flag the
  conflict to the researcher) rather than lumping both into one commit with
  a plain `git add <path>`.
- This is what makes "any single writing or analysis step can be identified
  and reverted from git history alone" actually true, rather than
  incidental.

`/data/` and `.env*` are gitignored and must never be committed, under any
circumstances (AD-9).

## Generated-artifact provenance format (AD-7)

Any generated `\input{}` or `\includegraphics{}` target under
`manuscript/generated/` (i.e. any file an analysis script produces and
Claude Code cites from `.tex` source, rather than a hand-typed value) must
carry a one-line provenance comment as its first line, in exactly this
format -- one canonical format, not "or a timestamp":

```
% Generated by <script path> @ <git-short-hash> -- do not edit by hand
```

- `<script path>` is the path (relative to the repo root) of the analysis
  script that produced the file -- any language, this convention does not
  assume Python.
- `<git-short-hash>` is the short git hash of the commit at generation time.
- The comment is written by the analysis script itself, as part of its
  handoff responsibility: a script writes its raw results to
  `analysis/outputs/` and is also responsible for placing (or directly
  writing) the citable subset -- with this provenance line -- into
  `manuscript/generated/`. This is never left as an unowned step.
- Binary generated targets (e.g. PDF/PNG figures) can't carry a leading `%`
  text comment as their first line. For those, provenance lives in a
  sidecar text file `<figure-file>.prov` next to the binary, containing the
  same one-line format.
- Files placed in `manuscript/generated/` are committed to git (tracked,
  not ignored) -- that is the entire point of this convention: it is what
  makes reversibility from git history alone actually true.
- This convention is tried where practical, not mechanically enforced: the
  researcher remains the final check before trusting a result (PRD
  counter-metric SM-C1). A wrong value silently inserted is worse than one
  that requires a manual check.

## Bibliography read + citation-key convention (CAP-1/CAP-2)

`manuscript/references.bib` is Better BibTeX's one-directional export from
Zotero (Zotero -> BBT -> `references.bib`). Claude Code only ever reads it.

- Always re-read `manuscript/references.bib` fresh from disk, in the same
  turn, immediately before validating or emitting any `\cite{key}` -- never
  rely on an earlier-session or cached view of the file's contents. A paper
  filed into Zotero can appear in a fresh export at any time; a stale view
  is not a valid basis for a citation.
- Never write a `\cite{key}` into any `.tex` file unless `key` is present
  in that same fresh read. If the key isn't there, don't invent, guess, or
  hand-type a plausible-looking one -- tell the researcher no such entry
  exists yet.
- Never hand-edit the bibliographic content of `manuscript/references.bib`,
  under any circumstances -- it is a generated export, not a hand-authored
  file. Any addition or correction to the bibliography goes into Zotero
  itself (via the researcher, or a later story's Zotero-filing capability),
  never into the `.bib` file's contents. This is about content, not git:
  committing the file after Zotero/BBT has updated it on disk is expected
  and normal, governed by the scoped-commit convention above like any other
  file -- it is not the kind of "edit" this rule forbids.
- Never invent, rename, or otherwise touch a citation key -- Better BibTeX
  owns key generation entirely; Claude Code only ever reads the keys it
  produces.
- If `references.bib` has zero entries, or is missing/unreadable, when a
  citation is needed, HALT and ask the researcher whether to wait for a BBT
  export or proceed some other way -- never fabricate a key to fill the gap.

## Project onboarding & the citation contract

This file holds only what is true of *every* instantiated project. Anything
negotiated with the particular researcher using this instance -- what the
project is about, which citation style it uses, which fields a reference must
carry, which Zotero collection is its root -- is not here. That is the same
mechanism/content split the rest of the template follows: mechanism lives in
this file and `.claude/skills/`; negotiated content lives at the repo root, in
`manuscript/`, `analysis/`, and `knowledge-base/`.

- **This instance's citation decisions live in `citation-contract.md` at the
  repo root.** It is generated by the `onboarding` skill from
  `.claude/skills/onboarding/templates/citation-contract.md`, and the generated
  file names that template path in its own header.
- **A fresh instance ships the template and no contract.** That absence is the
  signal, not an oversight: it means onboarding has not run here yet.
- **If `citation-contract.md` is missing, or the section you need still carries
  its placeholder marker -- the literal string `_not-yet-negotiated_` -- HALT
  and run the `onboarding` skill.** Never guess a citation style, never assume
  the template's proposal tables are a decision, never fill a placeholder with
  a plausible-looking default, and never let a citing or filing flow fall
  through to biblatex's implicit `numeric` default by omission. The same
  applies to a reference type the contract has no row for: ask the researcher
  and append the answer to the contract, rather than silently passing or
  silently blocking the item. Each reference-type table carries its own marker,
  so check the one on the table for the type in front of you, not the file as
  a whole.
- **The checking mechanism is not a per-project preference and is not here
  either.** How a Zotero item is checked against the contract on every touch --
  the Required-only rule, the external-lookup chain, Ask First on any recovered
  value, per-item accepted gaps -- lives in
  `.claude/skills/zotero-code-execution/SKILL.md` under "Field-completeness
  check", the skill through which every Zotero read and write goes (AD-8).

## Presentations

`presentations/<slug>/` holds Beamer (LaTeX) slide decks -- a sibling
deliverable to `manuscript/`, never inside it. Each deck gets its own
directory: `presentations/<slug>/main.tex` plus its own `images/` (static
images) and `generated/` (AD-7-provenanced figures copied from
`analysis/outputs/` or `manuscript/generated/`-style sources) subfolders.
Drafting and compiling a deck is driven by the `latex-presentation` skill
(`.claude/skills/latex-presentation/`), which writes `main.tex` directly
(no wrapper script, same shape as `subfield-lit-mapping`) from the
researcher's own Beamer template under its `templates/` folder by default,
then hands off to the existing `latex-compile` skill to build -- never
`latexmk`/`pdflatex` invoked directly, and never a second compile-error
parser reimplemented for slides.

The directory convention, the theming default-vs-override rule, and the
slides-specific figure-provenance and citation requirements are defined in
`latex-presentation`'s own `SKILL.md`, not duplicated in this file. Those
last two build on this file's "Generated-artifact provenance format" and
"Bibliography read + citation-key convention" sections, which the skill
names rather than restating.

## Obsidian research knowledge base

`knowledge-base/` at the repo root is an Obsidian vault for findings and
understanding built up while discussing papers with Claude Code. Obsidian
itself gets no skill wrapper: like VS Code + LaTeX Workshop (AD-1's
precedent), it is a separate human-facing app that reads the files Claude
Code writes directly.

No fixed note-type taxonomy, filename convention, or frontmatter schema is
imposed here. How notes get organized -- one per paper, one per idea, a
running log, whatever turns out to be useful -- should emerge from how the
researcher actually wants to use it, discovered through real use, not
decided upfront and imposed on them from the first session. If organization
becomes worth deciding (the vault has grown enough that structure would
actually help), ask the researcher how they want it done rather than
assuming a scheme.

`knowledge-base/` is on the content side of the mechanism/content split
described under "Project onboarding & the citation contract" above. The
convention itself lives only in this file, never as a template/example/
mechanism file inside the vault -- the vault holds only real,
researcher-approved content.

- **Always** offer to save findings at the natural end of a
  paper-discussion thread -- the researcher signals they're done, the
  conversation moves on, or they explicitly say to save/wrap up. Never
  silently skip the offer, never silently auto-save. If the thread ends
  with no explicit accept or decline, treat that as a decline for this
  thread -- nothing is written, and the offer doesn't carry over as
  pending.
- **Always** draft the content and get the researcher's approval before
  writing any new note, or new substantive content into an existing one.
- **Never** invent findings that weren't actually discussed in the
  conversation.
- Cleanup and organizing of existing notes (fixing links, deduplicating
  exact repeats, restructuring, renaming) can happen freely, without
  per-change approval -- as long as it doesn't change what a note actually
  says. Deleting a note, or merging two notes whose content actually
  differs, is a content change, not cleanup -- Ask First.
- A note about a specific paper can link to that paper's Zotero citekey
  (or a DOI/title if it isn't filed yet) when that's a natural thing to
  do -- not a mandatory schema every note must follow.
