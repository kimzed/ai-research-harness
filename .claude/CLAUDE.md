# AI Research Harness -- Project Agent Instructions

This file states three conventions that every later story in this repo
depends on. All are load-bearing: read them before writing any code or
making any commit here.

## Scoped-commit convention (CAP-9 / AD-9)

Every git commit Claude Code makes in this repo is scoped to exactly the
paths it wrote or changed in that turn.

- Never run `git add -A` or `git add .`.
- Before staging anything, run `git status` first.
- Stage only the specific paths written this turn (`git add <path> <path> ...`).
- For paths deleted or renamed this turn, use `git rm <path>` / `git add -u
  <path>` instead of a plain `git add` -- the same scoping rule applies.
- Any pre-existing uncommitted changes found in `git status` are left
  untouched and surfaced to the researcher -- never folded into a Claude
  Code commit.
- If a single path mixes pre-existing uncommitted changes with this turn's
  edits, stage only this turn's hunks with `git add -p <path>` (or flag the
  conflict to the researcher) rather than lumping both into one commit with
  a plain `git add <path>`.
- This is what makes "any single writing or analysis step can be identified
  and reverted from git history alone" actually true, rather than
  incidental.

`/data/` and `.env*` are gitignored and must never be committed, under any
circumstances (AD-9).

## Generated-artifact provenance format (AD-7)

Any generated `\input{}` or `\includegraphics{}` target under
`manuscript/generated/` (i.e. any file an analysis script produces and
Claude Code cites from `.tex` source, rather than a hand-typed value) must
carry a one-line provenance comment as its first line, in exactly this
format -- one canonical format, not "or a timestamp":

```
% Generated by <script path> @ <git-short-hash> -- do not edit by hand
```

- `<script path>` is the path (relative to the repo root) of the analysis
  script that produced the file -- any language, this convention does not
  assume Python.
- `<git-short-hash>` is the short git hash of the commit at generation time.
- The comment is written by the analysis script itself, as part of its
  handoff responsibility: a script writes its raw results to
  `analysis/outputs/` and is also responsible for placing (or directly
  writing) the citable subset -- with this provenance line -- into
  `manuscript/generated/`. This is never left as an unowned step.
- Binary generated targets (e.g. PDF/PNG figures) can't carry a leading `%`
  text comment as their first line. For those, provenance lives in a
  sidecar text file `<figure-file>.prov` next to the binary, containing the
  same one-line format.
- Files placed in `manuscript/generated/` are committed to git (tracked,
  not ignored) -- that is the entire point of this convention: it is what
  makes reversibility from git history alone actually true.
- This convention is tried where practical, not mechanically enforced: the
  researcher remains the final check before trusting a result (PRD
  counter-metric SM-C1). A wrong value silently inserted is worse than one
  that requires a manual check.
- CAP-9, AD-9, AD-7, and PRD counter-metric SM-C1 are canonically defined
  in SPEC.md in the harness planning repo (the sibling planning repo's
  `_bmad-output/specs/spec-ai-research-harness/SPEC.md`).

## Bibliography read + citation-key convention (CAP-1/CAP-2)

`manuscript/references.bib` is Better BibTeX's one-directional export from
Zotero (Zotero -> BBT -> `references.bib`). Claude Code only ever reads it.

- Always re-read `manuscript/references.bib` fresh from disk, in the same
  turn, immediately before validating or emitting any `\cite{key}` -- never
  rely on an earlier-session or cached view of the file's contents. A paper
  filed into Zotero can appear in a fresh export at any time; a stale view
  is not a valid basis for a citation.
- Never write a `\cite{key}` into any `.tex` file unless `key` is present
  in that same fresh read. If the key isn't there, don't invent, guess, or
  hand-type a plausible-looking one -- tell the researcher no such entry
  exists yet.
- Never hand-edit the bibliographic content of `manuscript/references.bib`,
  under any circumstances -- it is a generated export, not a hand-authored
  file. Any addition or correction to the bibliography goes into Zotero
  itself (via the researcher, or a later story's Zotero-filing capability),
  never into the `.bib` file's contents. This is about content, not git:
  committing the file after Zotero/BBT has updated it on disk is expected
  and normal, governed by the scoped-commit convention above like any other
  file -- it is not the kind of "edit" this rule forbids.
- Never invent, rename, or otherwise touch a citation key -- Better BibTeX
  owns key generation entirely; Claude Code only ever reads the keys it
  produces.
- If `references.bib` has zero entries, or is missing/unreadable, when a
  citation is needed, HALT and ask the researcher whether to wait for a BBT
  export or proceed some other way -- never fabricate a key to fill the gap.
- CAP-1, CAP-2, and AD-2/AD-4/AD-6 are canonically defined in SPEC.md /
  ARCHITECTURE-SPINE.md in the harness planning repo (the sibling planning
  repo's `_bmad-output/specs/spec-ai-research-harness/`).
